目前的結論

已修正 LFM 常沒有口語回覆的兩個可重現原因：工具格式不相容，以及預熱額度不足。 720p／1080p 的八次範例測試均有回覆，要求的看板與項目數也符合。

兩種解析度都未通過影音流暢標準。 目前保留真正的直式 720p；1080p 的播放拉長更明顯。不能把「有回答」或設定 25fps，當成實際不卡頓。

720p 與 1080p 指實際輸出像素。現有數字人是直式素材，因此分別為 720×1280 與 1080×1920；只把高度設成 720，輸出約 404×720，並不符合本次最低畫質要求。

為什麼 LFM 常沒有回覆

以實際 GGUF、OpenAI 相容串流及正式回覆解析器，重複執行控制台的四個範例。舊設定會產生 <|tool_call_start|>[BOARD(MODE:BOARD)]<|tool_call_end|>，內容沒有可朗讀的答案；前端接到完成事件，也不能因此算作回答成功。

修改了什麼，以及原因

  1. 讓預熱請求有足夠額度。 依官方模型卡，LFM2.5-2.6B 是持續思考型模型。舊預熱只有 16 tokens，會在 reasoning_content 階段結束，健康檢查因此一直未就緒。改為 64-token 思考預算＋32-token 可見格式空間。
  2. 讓小模型輸出可播放的格式。 LFM 使用溫度 0.1、重複懲罰 1.1、64-token 有限思考，以及簡短的格式提示。依llama.cpp GBNF 格式限制口語與看板語法，包含思考結束標記，避免全部輸出被分類成不可見的思考內容。模型仍根據使用者可編輯的 Rules 選擇 SIMPLE／BOARD；沒有加入關鍵字路由。
  3. 修正跨片段解析。 工具呼叫完整隔離，內容不能混入語音或對話歷史；只有工具內容時回報格式錯誤。看板標記分拆到單一字元時，完整等到雙括號結束，修正不存在的正規表示式群組造成的例外。
  4. 最低輸出改為真正的直式 720p。 一般、朗讀與診斷設定的高度上限均改為 1280，寬高比維持 9:16。設定為 25fps，保持 TensorRT UNet 與 TAESD；LFM 模型及使用者保存的語音、助手與背景偏好繼續使用。
  5. 保留先前已修正的音訊路徑。 音訊按剩餘的 20ms 時間預算送出、影片使用實際釋放時間戳、暫停麥克風不做多餘處理，以及 160ms 音訊緩衝。這次不以退回低解析度或鬆綁測試門檻取得通過。

既有的音訊排查、解碼器畫質與舊設定測試，請閱讀前一份完整改善報告；其中 450／540 高度是當時的歷史設定。

驗證與實用限制

新增與相關回歸測試 121 項通過。專案整合／品牌檢查通過；完整 Python 測試為 505 通過、4 跳過、1 效能失敗；前端 84 項測試與正式建置通過。未通過的項目是原有高解析度背景合成預算測試：1080×1920 合成約 39.48ms，超過既定 30ms 預算，沒有放寬門檻。此項失敗也支持目前高解析度影音路徑仍需優化，不能宣稱已完全流暢。

模型單獨測試不載入 TTS 或數字人，用來分離語言模型的延遲；解析度測試則經過正式後端、實際數字人、WebRTC、Chromium 畫面回呼及接收端 PCM。每次回覆都保存原始指標，失敗測試也保留。

播放通過標準：實測至少 23fps、顯示間隔不超過 120ms、零 WebRTC 凍結、零音訊遺失補償；聲音跨度不得超過同段 Edge TTS 參考音訊的 1.15 倍。零封包遺失不能證明伺服器沒有插入靜音。畫面幀率測試沒有逐幀讀取嘴部像素，因此不能單憑這些指標證明所有口型都正確。

TAESD 仍是近似嘴型解碼器：提高輸出解析度不等於恢復完整 VAE 的牙齒與唇部細節。有限次測試也不能保證未來所有問題與任意桌面負載都流暢。

官方資料：LiquidAI 模型卡（持續思考型模型與解碼建議）；llama.cpp GBNF 文件（格式約束）。

檔案與重現方式

原始結果在 .scratch/lfm-resolution/：model-before-strict.json、model-final-v2.json、model-final-v3.json、720p/playback.json、1080p/playback.json。瀏覽器重現：uv run --with playwright python .scratch/lfm-resolution/playback_probe.py --height 1280 --output .scratch/lfm-resolution/recheck（先啟動服務；1080p 使用高度 1920 與對應設定）。此命令會占用一個控制台連線。
