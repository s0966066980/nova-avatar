# 控制台與數位人舞台各自對話

Status: implementation-complete

實作與自動化驗證已完成；真人麥克風、喇叭與瀏覽器現場驗收尚未完成，
限制與結果見文末。

日期：2026-10-29。使用者指定 grill-with-docs，結合 grilling 與
domain-modeling；使用者已接受 Q1–Q3 並確認完整共同理解，授權開始實作。

## 問題與目標

使用者回報控制台模式無法正常對話，數位人舞台麥克風也會卡住；要求移除
「控制台測試／訪客模式」，讓控制台與舞台如 Jetson Orin 版各自運作。
這是執行狀態與操作隔離；兩端仍會共用主機運算資源。

## 已確認決策

- Q1：保留 PC 多角色交接、天氣、雙語、附件與對話功能。兩端各自維持
  目前角色、對話記憶、語系、麥克風、影音、字幕與看板，移除全域輸入模式
  切換與問答同步播放。招呼僅屬於舞台；自動清場原限定舞台，已由
  [後續控制台清場修正](../console-idle-reset/spec.md) 擴充為兩端各自執行。
- Q2：共用可選用的設定檔、模型與素材；修改並儲存設定不打斷舞台當前
  對話，由舞台下一場對話採用。舞台外觀等明確管理操作仍可直接更新舞台。
- 控制台對話與舞台對話為不同場次，不以「控制台測試模式」命名；訪客
  身分及舞台服務訪客的職責繼續存在。

## 已查證事實

- PC 的 ADR-0017、ADR-0019 與 Jetson 移植規格 Q1/Q9 明文採用單一
  輸入來源與同步展示；本需求取代這些限制。
- `RoleCoordinator.input_allowed` 同時影響文字送出與麥克風閘門；只移除
  UI 按鈕仍會拒絕另一端輸入。`RoleCoordinator._switch` 會中斷並重新綁定
  所有工作階段，`SessionPresentation` 亦只有一個共用影音來源。
- 停止／返回主角色及舞台自動重置仍可能經全域角色協調器影響另一端，
  必須與輸入、影音一併調整。這些事實說明架構與新需求的衝突，尚未證明
  使用者實機故障的完整原因。
- Jetson 參考：`origin/jetson-orin`，commit
  `1b61a2190585b19b37c953481ed2970ee6b7054c`。兩端各自建立 avatar、
  VoiceTurnSession 與 HumanPlayer，沒有 PC 的全域角色協調器。
- Jetson 控制台連線後初始暫停收音，按麥克風才開始；舞台沿用免按對話
  與既有文字輸入啟用流程。沒有跨頁裝置鎖，兩頁都啟用時可能收到同一
  實體麥克風的聲音；實際瀏覽器與裝置能力仍須驗收。
- Jetson 的模型／Prompt 管理設定仍可更新既有實例；部分引擎或素材更新
  要求全部工作階段斷線。因此 Q2 是本次明確接受的改進，不能宣稱 Jetson
  已完整提供延後套用語意。Jetson 亦沒有 PC 的多角色交接。

## 最後一輪：已確認邊界

- Q3：舞台下一場對話始於 60 秒完整重置完成或重新連線；15 秒清畫面、
  角色交接及手動清空不套用新預設。
- 模型、STT／TTS 等無法安全熱切換的共用資源標示待套用，等兩端斷線後
  更新，絕不自動中斷另一端；控制台先按麥克風才收音，舞台維持免按對話。
- 使用者以「是，確認完整方案並開始實作」接受上述邊界與整體設計。

## 實作驗收範圍

- 雙端同時文字／語音對話；一端停止、插話、返回、角色交接、清空、
  斷線及重連皆不取消另一端輪次，也不混用影音、字幕、附件或記憶。
- 舞台收音不再受控制台模式或操作鎖住；控制台可獨立啟動與暫停收音。
- 舞台招呼、15 秒畫面清除、60 秒完整重置及空場後 30 秒招呼間隔
  繼續適用，不影響控制台對話。
- 驗證舊輪次與新設定不混用；共用資源待套用設定須保留至成功套用，亦須在重啟後可復原。
- 編輯時執行聚焦測試；交付前完成 `uv run ruff check .`、
  `uv run python scripts/check-integration.py`、`uv run pytest`，以及
  `web/` 的 `npm run lint`、`npm test`、`npm run build` 與品牌授權稽核。
  自動化與實體麥克風／瀏覽器驗收分別記錄。

## 實作與驗證紀錄（2026-10-29）

- 每場對話使用自己的 `ConversationRoles`、角色設定快照與影音軌；
  移除全域輸入模式及跨頁問答分送。停止、返回、交接與斷線只作用於
  指定場次；控制台對話與舞台招呼、清場互相隔離。
- 新舞台對話在完整自動重置或重連時取得新預設；手動清空、交接及
  清畫面保留原設定。共用資源更新等待兩端皆斷線，待套用資料保存至
  本機，後端重啟時會重新嘗試套用。
- 收尾回歸找出並修正兩個邊界問題：待套用項目原本在磁碟寫入成功前
  就從記憶體移除，導致寫入失敗後無法在同一程序重試；WebRTC 原本在
  等待請求內容前檢查資源狀態，可能於重載開始後仍建立連線。
  現在先完成原子寫入才發布新待套用清單，並在讀完連線請求後檢查
  資源狀態，再保留連線名額。新增五個案例先確認失敗，修正後通過。
- 聚焦驗證：`uv run pytest tests/test_deferred_settings.py
  tests/test_webrtc_lifecycle.py -q`，21 passed。
- 完整 Python 驗證：`uv run pytest`，763 passed、3 skipped，77.80 秒。
  Ruff 與 `scripts/check-integration.py` 通過，包含品牌與授權文件契約。
- Web：`npm run lint`、`npm test`、`npm run build` 通過，144 個測試
  全數成功；建置保留既有的大型 bundle 與空 bootstrap chunk 提醒。
  README 已同步更正為兩端各自對話。

本次瀏覽器工具回傳 `apps: []`、`browsers: []`，因此沒有進行真人
麥克風／喇叭、雙頁實際裝置收音或 GPU 同負載的嘴型現場驗收。
上述自動化驗證不代表這些實體項目已通過。

## 後續修正：快捷指令與舞台初始收音（2026-10-29）

- 快捷指令固定切回對話模式並送出。已連線的一般對話路徑原本可送出，

- 舞台原先在文字／附件開啟時主動跳過麥克風請求，造成進入後必須再點

- 以真實 App／ConversationComposer 元件測試快捷指令；舞台腳本測試

## 快捷指令再次回報：已連線仍無立即回饋（2026-10-29）

使用者確認控制台顯示 WebRTC 已連線，點擊後沒有輸入文字或錯誤提示；
上一輪的模式切換與未連線提示未解決現場回報，不能把那輪測試通過當成
本次問題已排除。

比對舊版發現舊版先顯示使用者問題再等待 HTTP，新版等待附件元件收到
HTTP 回應後才加入訊息。加入延遲 HTTP 的實際 App／Composer 元件測試後，
重現請求已送出但畫面完全沒有問題文字的狀態。此為已確認的回饋缺口，
並非宣稱已取得使用者瀏覽器內的完整故障原因。

- 快捷指令明確將問題文字傳入送出方法，無須依賴 v-model 往返後再讀取。
  一般輸入、附件與快捷指令仍共用附件驗證、輪次與取消流程。
- 點擊後先顯示暫存問題及「傳送中」，後端接受後以同一則訊息確認，不
  重複建立；拒絕時移除暫存紀錄、保留草稿並顯示錯誤。傳送中再點快捷
  指令會提示等待，不覆蓋第一個問題。
- 使用與 Vite 開發模式相同的分離 template 編譯方式驗證元件，加入
  慢回應、拒絕、連點、取消及晚到舊回應案例；前端共 155 passed，
  lint 與 production build 通過。Python 763 passed、3 skipped，78.03 秒；
  Ruff、整合與品牌授權檢查通過。
- 本次查核途中 3000／8010 服務已停止，瀏覽器工具仍沒有可用表面。
  已請使用者重新啟動並點擊，以便對照實際請求紀錄；現場結果尚待確認。
