## 計時語意

沿用 CONTEXT.md 的「首音延遲」：確認使用者發話結束後，到送出該輪
第一個非靜音 WebRTC 回覆音訊幀。使用者停口到系統確認結束的時間，
以及送出到瀏覽器聽見的時間，都需要另外記錄，不能省略或混為一個起點。

`voice_session.py` 第 540–542 行同時開始 LLM 首內容、總生成與首片段計時；
第 739–748 行在第一片段註冊時同時開始 TTS、MuseTalk、WebRTC 計時。
故首音關鍵路徑為 5.427 + 1.994 秒；不能再把同一起點的
0.489、0.668、1.916、1.994 秒逐項相加。

`llm_first_token` 在協定解析之前標記，表示 API 的第一個 delta.content。
它可能是模式標記，並不是第一句可朗讀文字；也不含單獨的
reasoning_content。因此不等同嚴格的模型第一 token。

## 證據支持的瓶頸

1. LLM 第一內容約 3.8 秒已超過「2 秒開始回答」的候選目標；
   後續形成首個可播片段又花約 1.6 秒。
2. 現行耦合路徑先等 MuseTalk 結果，再 enqueue PCM；此輪首 PCM
   已有後仍約等 1.5 秒。`src/avatars/base.py` 第 481、537 行，
   `src/avatars/musetalk/avatar.py` 第 367 行可核實這個順序。
3. 17:25 的實際播放另外有 534–622ms 的反覆 pacing stalls，
   並有一次 882ms；首音等待與播放連續性需要不同驗收指標。
4. 第一片段 TTS 首 PCM 約 0.49 秒；第二片段約 1.46 秒，存在長尾，
   但不能把第一輪約 7.4 秒全部歸因於 TTS。
5. 前次 VAE、解析度與獨立音訊只在隔離實驗測試，未在此輪設定生效。

## 必須保留的不確定性

- 沒有本輪 VAD、ASR 與瀏覽器首音時間，不能量化其占比。
- 尚未把 LLM 等待拆成 prefill、模型生成、排程／GPU 競爭與輸出協定等待。
- `openai.py` 第 62 行對新引擎設定至少 1024 token 的上限，
  本輪配置值 788 的實際請求變為 1024；這是設定一致性問題。
  上限不代表一定生成滿 1024 token，也不能單獨解釋首內容慢。
- 自行啟動 llama-server 的程式已有 `--reasoning off --reasoning-budget 0`；
  尚未核對每次實際服務的 chat template 與啟動旗標，不能假定 thinking 開啟。
- AUTO 協定下沒有模式標記的回答可能延後到 flush；沒有本輪證據證明
  此路徑發生，應以去識別解析事件驗證，不能直接認定。

## 候選解法與依賴

先補齊真實語音輪次的全鏈路計時，再用相同問題集確認效果。
優先研究 LLM 首內容與首短句：核對 GPU offload、prompt/context 長度、
生成速度與協定等待；回覆可先形成一個短而完整的結論，再展開內容。
保留可播回覆片段與看板隔離，避免以硬切文字換速度。

解析度控制與 TensorRT VAE 有實测改善，可降低後段成本，
但 batch 8 的 UNet + VAE 仍約 618ms，模型部分約 13fps。
這不足以保證 25fps 嘴型或 2 秒首音。

獨立音訊能解除嘴型對 PCM 的阻擋；前次 6 秒 PCM 約 6 秒播完，
但嘴型同步未通過驗收。是否採用必須先決定可接受的嘴型品質，
不能默認成為正式路徑。候選解法皆尚未部署。

前次實驗資料：[avatar-performance/report.md](../avatar-performance/report.md)。
相關決策：[ADR-0007](../../docs/adr/0007-stream-replies-with-turn-isolation-and-audio-clock.md)。

## 第一輪已接受決策

- Q1：優先「停口後 2 秒內真正開始回答、播放不中斷，口型另驗收」，
  或「3 秒內開始回答且口型同步」，或先量測再定門檻。
- Q2：限定現有 Jetson，或接受區網 GPU 主機，或付費雲端運算。

使用者回覆「根據建議」，採用兩項建議：

- 感知首音延遲以 2 秒內為目標，回覆播放連續性必須驗收，嘴型同步另行驗收。
- 第一階段限定現有 Jetson，先排除本機軟體等待，再評估硬體需求。

2 秒是目標，尚不是已達成的保證。提示音及「請稍等」不算真正回答。
CONTEXT.md 已區分感知首音延遲、既有伺服器首音延遲與回覆播放連續性。
上述取捨先記錄於本規劃；尚未決定切換模型或部署實驗性嘴型路徑，
也沒有新的難以逆轉架構選擇，因此不建立新 ADR。

## 第二輪已接受決策

Q3：服務先預熱完成再開放對話，以就緒後 P95 感知首音 ≤2 秒驗收；
或啟動後立即開放，連第一輪都要求 ≤2 秒。
使用者已明確選擇前者，不能以提示音、占位語或把預熱算成對話來替代回答首音。
服務啟動時間與就緒後回應時間分開報告，嘴型同步仍另驗收。

現有啟動已包含 MuseTalk UNet/VAE dummy batch、Edge 首 encoded packet
及模型載入。候選方案補的是實際 prompt 預填、完整 PCM 與特徵／編碼
路徑，不是重複載入模型。是否改善冷／暖差異仍需對照測試。
