# Nova Avatar 感知首音與播放連續性改善

Status: implementing

## 使用者已接受的目標

感知首音延遲以 2 秒內為目標：使用者結束發話後，聽見真正的回答內容，
而非提示音、空白音訊或占位語。回覆播放連續性同時驗收；嘴型同步另驗收。
第一階段使用目前 Jetson，優先排除軟體等待。

## 既有證據

17:25 真實輪次從 LLM 開始到 WebRTC 首音約 7.42 秒，其中首內容約
3.79 秒、形成可播片段約 1.63 秒、TTS 首 PCM 約 0.49 秒，
首 PCM 到 WebRTC 又約 1.51 秒。VAD、ASR 與實際瀏覽器播放尚缺測量。
目前串流已開啟；解析度控制與 TensorRT VAE 尚未套用。
完整來源與計時起點見 [analysis.md](analysis.md)。

## 第一階段範圍

先建立完整語音輪次基線，區分感知首音、伺服器首音、首個可播片段及
播放額外停頓。沿用既有模型、TTS、回答協定與輪次隔離，先確認
GPU offload、prompt/context、首完整短句、設定覆写與推理路徑的等待。

將已驗證的解析度控制與 TensorRT VAE 作為隔離 A/B 配置，確認實際
啟動及持久化覆寫後仍生效。獨立音訊另作實驗，不以未通過的嘴型同步
結果宣稱完整數字人品質已達標。

## 驗收原則

- 2 秒目標包含發話結束判定、STT、LLM、TTS、媒體送出及接收播放。
- 分階段指標標示計時起點；重疊區間不得相加。
- 缺漏的 VAD、ASR 或瀏覽器時間標為未測，不以零補齊。
- 播放停頓與來源音訊的自然語意停頓分開；PCM 順序及完整性保留。
- 使用相同問題、模型暖機狀態與有效設定做 A/B，報告分位數與樣本數。
- 保留插話、generation fencing、片段順序、已播回覆提交及看板隔離。
- 不以放慢音訊、硬切語意或占位回答交換指標。

## 待量測的限制

同模型軟體改善的實際可達速度仍待量測。若 LLM 首內容本身無法進入
2 秒總預算，需再決定是否接受模型品質或硬體取捨，不默認換模型。
第一階段方案及預熱驗收已接受；實際可達速度以隔離對照量測為準。

## 可審閱的第一階段方案

1. 補齊 VAD、STT、LLM 可播文字、TTS 可用 PCM、媒體入列及接收端
   起音的數值測量；保留既有指標定義，缺測明確顯示。
2. 使用既有回覆規則介面，只調整口語規則：先給約 10–20 字、直接回答
   問題的完整短句，以句號結束，再補說明。保留模式標記、看板規則與
   版本檢查；只對新輪次生效，不另發第二次模型請求。
3. 統一引擎新建、控制台更新與重啟後的實際 token budget，保留看板
   JSON 的預算。這是設定一致性修復，不把 token ceiling 當成首音保證。
4. 在隔離設定中 A/B 測試 540×960、TensorRT VAE、獨立音訊；
   每次記錄合併 runtime overrides 後的有效旗標，避免只有 YAML 改動。
   音訊與嘴型各自報告結果；失敗嘴型不得被音訊通過掩蓋。
5. 對後續 Edge TTS 首音長尾、重試及預取順序作連續性測試。
   不以重疊片段或丟棄尚未播放的回答交換速度。

現有模型最新一輪第一個 content 只有 0.134 秒，因此第一階段不切換
模型、不移除看板、不更換聲音；先量測同配置下的可重現改善。
較慢輪次的原因仍須分辨 prefill、快取、上下文及 GPU 排程。

## 第二輪已接受驗收

使用者已選擇：服務預熱後才開放對話；就緒後以 P95 感知首音 ≤2 秒
驗收，啟動時間單獨列出。不把兩筆不同輪次的耗時差直接當成預熱因果證據。

## 最新重點

使用者補充：LLM 已輸出完整內容，但數字人語音仍斷斷續續。
第一優先是完整文字已準備好時的 TTS 片段銜接與 PCM 播放連續性。
以固定三句完整文字做真實 Edge TTS + MuseTalk + WebRTC 對照，
排除 LLM 尚未生成文字的因素；首音目標與預熱工作繼續保留。
