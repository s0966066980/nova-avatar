# 首音延遲改善

Status: ready-for-agent

使用者已確認 Q1–Q23 與本規格（2026-10-30）。

## 現況（2026-10-29 實際語音輪次，自 VAD 判定說完起算）

| 階段 | P50 | P95 |
|---|---|---|
| 語音辨識（Whisper small、auto 語系、beam 5） | 0.48 s | 0.57 s |
| 辨識完到主回答開始（路由 LLM、RAGFlow、模型資訊查詢，串行） | 1.55 s | 3.92 s |
| 主回答開始到第一個可播回覆片段 | 0.85 s | 1.27 s |
| 片段到第一個 WebRTC 音訊送出 | 0.62 s | 0.88 s |
| **首音延遲（估算）** | **3.57 s** | **6.19 s** |

主因：llama-server 啟動時只放 31 層進 GPU（生成約 35 tok/s，全 GPU 時 107–124）；
路由、檢索、主回答串行；每輪三支模型資訊查詢；開口前多播約 0.2 s 待機靜音
（10/17 起的回歸）；Whisper 設定偏慢。現有 1.19 s 基準是 9 月、無 RAG／路由、
以「伺服器接受 Prompt」起算的數字，不再代表現況。量測細節見本目錄 issue 01。

## 目標

以**感知首音延遲**（`CONTEXT.md`）判定；同時回報首音延遲與「伺服器接受 Prompt」起算的延遲。

| 階段 | 情境 | P50 | P95 |
|---|---|---|---|
| 第一階段 | 舞台語音一般輪次 | ≤ 1.2 s | ≤ 2.5 s |
| 第二階段 | 舞台語音一般輪次 | ≤ 1.0 s | ≤ 1.5 s |
| 第一階段 | 觸發 RAG 檢索或交接的輪次 | ≤ 1.6 s | ≤ 3.0 s |

## 已確認的決定

- **量測先行**：先建立真實 WebRTC 量測工具並量出基準線，每項優化以同一工具驗收（Q14）。
- **路由並行**：路由與檢索同時開始，主回答不等路由；路由判定不交接後才放行音訊；檢索上限 400 ms（[ADR 0022](../../docs/adr/0022-run-routing-retrieval-and-answer-concurrently.md)，Q7、Q8、Q15）。
- **LLM 全 GPU**：llama-server 先於 MuseTalk 啟動；放不下全部層數即啟動失敗並說明，非全 GPU 時控制台與健康檢查顯示警告（Q9）。
- **主要 LLM 改為 Gemma 4 E2B**（`gemma-4-E2B_q4_0-it.gguf`，Apache-2.0；附件共用同一服務）。9B 保留為可選模型。以固定 30 題、自動檢查與並排報告驗收品質，由使用者決定是否接受；路由準確率不足時改用關鍵字初篩＋E2B，不回頭用 9B（Q17、Q18）。
- **語音辨識**：Whisper 依對話語系固定語言、beam 1、記憶體直傳；與 FunASR 用同一批錄音比較速度與字錯率後擇一（Q10）。
- **第一個片段**：先以 Prompt 規則讓模型以簡短完整句開頭；不足時才讓第一個片段停在可獨立朗讀的子句，並同步修改術語表與 ADR 0007（Q4）。
- **不加墊話**（Q5）。
- **TTS 改為 BreezyVoice**（聯發科，Apache-2.0，原生台灣華語），放棄串流（Q19）。聲線使用使用者自錄或有書面授權的台灣華語參考錄音；錄音備妥前以範例錄音開發，不作正式預設（Q22）。第一個片段（約 15 字）合成 P50 ≤ 0.4 s、P95 ≤ 0.7 s；達不到依序：縮短首句 → 加速 BreezyVoice → 改用 Fun-CosyVoice3＋台灣讀音字典（Q23）。
- **Edge TTS 降為開發用**：它使用非公開端點，無正式商用授權，場域斷網即無法發聲（Q11）。
- **顯存優先序**：LLM 全 GPU 優先；本機 TTS 放不下時換更小的 LLM（Q13）。
- **授權標示**：Fish（年營收 50 萬美元門檻）、IndexTTS2（用戶數／營收門檻）、XTTS（非商用）比照 Wav2Lip 標示；Edge TTS 標為開發用；補 Gemma 4 聲明（Q21）。
- **停用 11434 的預設 Ollama**；不明 python 程序只調查回報，不自行終止（Q21）。
