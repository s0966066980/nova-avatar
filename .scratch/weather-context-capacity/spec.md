# 天氣助手一週追問的 Context 容量修正

Status: implementation-complete

日期：2026-10-29。使用者依序詢問「今天台北天氣如何？」及「未來一週
天氣如何」時，第二題出現 `context_capacity`；返回主數位人後一般對話
可正常進行。沿用 diagnosing-bugs 先建立真實模型回饋，再修正與回歸。

## 重現與原因

```bash
uv run python .scratch/weather-context-capacity/validation/reproduce.py --real-model
```

使用保存的 Qwen3.5 9B 設定、8192 Context、CWA 臺北市當日／一週資料、
正式 AUTO 協定及第一輪已顯示看板回條，在獨立本機模型服務重現：
第一題成功；第二題實際輸入 7605、預留回答 788，合計 8393，拋出
`context_capacity`。保留[修正前結果](validation/before.json)及第一輪狀態。

一週資料有 90 個氣象值、14 種時間區間，舊格式在各氣象因子下重複
序列化時間。一般主角色對話沒有此份氣象資料，因此不觸發同樣容量
壓力。先前使用簡短假回覆而沒有看板的重播尚能通過；納入真實 AUTO
回覆與看板後，才精確重現使用者的連續追問模式。

## 修正

- 只調整交給 LLM 的預報表示：相同 start／end 的氣象因子共用一列，
  明示各值屬於該列有效區間。原始 API 結果與快取繼續使用原格式。
- 保留每筆氣象值、時間、單位名稱、來源、發布／取得時間、機率缺值
  與前三天機率覆蓋範圍。不同區間及同因子同區間的衝突值仍分開。
- 不變更 Context、回答預算、歷史保留、已顯示看板或角色記憶邊界。
- 以原本第一輪的完整歷史與看板重播第二題，實際模型成功回答；
  輸入由 7605 降至 3568，回答仍預留 788，合計 4356。
  見[保留第一輪的重播](validation/replay-first.json)。

聚焦 `test_weather_context`、CWA、角色協調及反向交接共 64 passed。
