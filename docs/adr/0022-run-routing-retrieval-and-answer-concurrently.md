# 路由、檢索與主回答並行，路由判定後才放行播放

2026-10-29 實測的語音輪次中，辨識完成到主回答開始之間約 1.5 秒（P95 3.9 秒），
因為每輪依序等待角色路由的 LLM 呼叫、RAGFlow 檢索與 llama-server 的模型資訊查詢；
這段時間直接落在**感知首音延遲**上。

改為路由與檢索同時開始；主回答不等路由，只等檢索完成或達 400 ms 上限就以目前
角色開始產生。可播回覆片段照常合成，但在路由判定「不交接」之前不送出任何音訊。
路由判定交接時，以既有的輪次隔離取消主回答，改走交接流程，被取消的片段不會播出。
檢索逾時就不帶檢索結果回答，控制台顯示「本輪未取得檢索」，與既有的故障語意一致。
模型資訊查詢改為快取，移出每輪路徑。

## 取捨

- 交接輪次會多花一次被丟棄的主回答生成；換來一般輪次幾乎省下全部路由時間。
- 檢索上限收緊後，慢的知識庫可能較常落空；以控制台狀態讓管理者察覺，而不是讓
  每輪多等。
- 捨棄的方案：關鍵字或向量初篩後才呼叫路由（仍有一次串行等待，且漏判會讓交接
  失效）；維持串行（無法達到首音目標）。

細節與驗收見[首音延遲規格](../../.scratch/first-audio-latency/spec.md)。

## 2026-10-30 補記：檢索上限暫調為 700 ms

400 ms 上限實測 24 輪中 22 輪逾時，等於關閉 RAG。使用者決定（Q25）先把上限調為
700 ms，再加速 RAGFlow 檢索，最終上限依加速後實測另定；本文上方的 400 ms 為原始
決定，保留不改。拆解（issue 15）：RAGFlow 檢索 P50 約 0.55 s，其中約 0.47 s 是
bge-m3 查詢嵌入（Ollama，與其他模型共用 GPU）；Elasticsearch 約 20 ms，其餘處理
約 30 ms。RAGFlow API 不接受用戶端提供的查詢向量，`page_size`、相似度門檻、
候選數等選項在量測誤差內，因此加速要在嵌入服務端進行。
