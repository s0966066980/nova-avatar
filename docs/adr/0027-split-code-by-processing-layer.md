# 依處理層劃分程式；STT、LLM、TTS 以 loopback 服務為目標，Avatar 留在核心行程

為了讓程式日後容易交給不同的人維護，也能單獨拆成行程，程式依**處理層**劃分，不依引擎劃分（用語見 `CONTEXT.md`）。劃分方式如下：

- **核心**：輪次編排、WebRTC、VAD、對話與數位人設定檔、config、閒置招呼。
- **語音轉文字**。
- **回答模型**：包含 RAGFlow、網頁搜尋、交接判斷、天氣工具與 AI 招呼生成。
- **語音合成**：包含音訊庫、聲線模型與聲線訓練。
- **數位人渲染**：MuseTalk 與綠幕合成。

各處理層之間不直接互相呼叫，一律經由核心。

## 目標架構

STT、LLM、TTS 的目標形式是只聽 `127.0.0.1` 的服務。數位人渲染留在核心行程內，只用程式介面隔開，原因是它每 20 ms 就要接收音框、輸出視訊幀，並且必須對齊音訊主時鐘（ADR 0007、0008）。跨行程傳遞會直接影響首音延遲與嘴型同步。

邊界規則：

- **狀態歸屬**：輪次狀態全部由核心持有，包括角色對話記憶、對話附件、數位人設定檔、回覆規則、當次角色組合、輪次隔離與片段播放柵欄。處理層只持有自己的資產：TTS 持有音訊庫、聲線模型、訓練語料與訓練工作；LLM 持有 RAGFlow 連線。服務不記住任何一場對話，核心每次呼叫時都帶齊這一輪所需的資料。
- **可播回覆片段由核心切分**：LLM 只送出口語文字增量，以及看板、檢索參考、網頁來源等結構化事件；完整語意邊界、語意等待上限與回覆背壓都留在核心。
- **數位人渲染不持有 TTS**：核心取得 TTS 輸出的 PCM 後交給數位人渲染。Edge 的重試與熔斷屬於 TTS 層內部。
- **交接判斷、天氣工具、AI 招呼生成**都是對 LLM 提出的請求，所以歸 LLM 層。當次角色組合、交接規則與場域預設地點這些資料仍由核心持有，每次請求時帶入。ADR 0022 的並行要求改由核心同時發出交接判斷與回答請求來達成。
- **聲線訓練能否開始**：舞台連線由核心檢查，剩餘顯存由 TTS 層自己檢查。
- **前端只和核心溝通**：服務沒有自己的驗證，路由分類仍依 ADR 0021。

## 拆成行程時的規則

- **傳輸**：使用 loopback HTTP。
  - STT：`POST` 音訊，回傳 JSON。
  - LLM：以 SSE 串流回覆事件。
  - TTS：每個可播回覆片段一個請求，以 chunked 回傳 16 kHz s16le PCM。
  - 取消的方式是由核心斷開連線，`turn_id` 只用於記錄。
- **行程監督**：沿用 Owned llama-server 的模式，由核心啟動、檢查健康狀態並重啟服務，部署設定仍然只有一份。設定中可以填 `url`，讓核心改連開發者自行啟動的服務。控制台切換引擎時，呼叫該服務的 `PUT /engine`。
- **版本相容**：服務在 `/health` 回報 `contract_version`，版本不符時核心拒絕使用，並在控制台顯示原因。
- **延遲驗收**：每拆出一層，首音延遲 P50 的增加不得超過 50 ms，P95 不得超過 100 ms，未達標就不合併。拆分順序為 STT → LLM → TTS。

## 何時拆

2026-11-26 時專案只有一位主要維護者，所以目前只做到「程式介面隔離＋資料夾劃分」，不拆行程。出現具體需求時才把某一層拆出去，例如有人接手某一層、依賴互相衝突、需要單獨重啟，或要把 LLM 移到另一台機器。

## 捨棄的方案

- **連數位人渲染也拆成網路服務**：每 20 ms 跨一次行程，首音延遲與嘴型同步的風險過高。
- **只做程式介面，不先訂下目標架構**：介面可能被設計成依賴回呼或共享物件，日後無法搬到網路上。
- **gRPC**：這幾個介面用 HTTP 已經足夠，改用 gRPC 只會多出 proto 工具鏈的成本。
- **跨機器水平擴展**：一個場域只有一台主機與一張 GPU，不需要。
